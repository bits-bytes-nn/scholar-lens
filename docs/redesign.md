# Scholar-Lens 재설계안

상태: 검토용 초안(2026-11-03). 승인 전에는 구현하지 않습니다. 현재 동작의 정본은 `docs/design.md`입니다.

## 1. 결론

- 코드는 헥사고날 구조(도메인 / 응용 / 포트 / 어댑터 / 진입점)로 한 번에 재구성합니다. CLI·`JobRequest`·`JobResult`·종료 코드·Batch 작업 정의·블로그 규칙 계약은 그대로 둡니다.
- 생성 방식은 "결정론적 뼈대 + 범위가 정해진 에이전트 노드 + 주장 단위 검증"으로 바꿉니다. 파이프라인 전체를 자율 에이전트 하나에 맡기지 않습니다.
- 품질 개선의 중심은 근거 장부(evidence ledger)입니다. 에이전트가 원문을 필요한 만큼 읽으며 인용문과 위치가 붙은 근거를 모으고, 개요가 근거를 절마다 한 번만 배정하고, 작가는 배정된 근거만 인용 표시와 함께 쓰고, 검증은 표시된 근거와 주장을 대조합니다.
- 에이전트 실행은 Strands Agents(Python SDK, Bedrock 기본 제공자)로 구현하고 `AgentRunner` 포트 뒤에 둡니다(3.5). 단발성 구조화 호출과 문장 생성도 같은 Bedrock 모델 어댑터를 씁니다.
- 지금 코드의 취지(출처 권한, 용어집, 한국어 문체, 블로그 규칙 게이트, 두 단계 서베이, 카드 캐시, 인용 검증, SSRF 방지, 작업 계약)는 모두 유지하고, 구현 위치와 강제 방식만 바꿉니다(2.4).
- 글 품질의 기준은 기존 결과물과 사람 수정 이력에서 뽑은 글쓰기 원칙(5.1)입니다. 사람이 가장 많이 고친 것은 수치의 범위·단위·출처와 인용 링크였으므로, 이를 근거 필드와 코드 검사로 막는 것을 우선합니다.
- 4종 글(리뷰, 요약, 가이드, 서베이)은 하나의 생성 엔진을 쓰고, 종류별 차이는 `ArtifactSpec`(자료 수집, 개요 틀, 분량, 마무리)으로 둡니다.
- 전환의 합격 기준은 고정 평가셋에서 현재 main 대비 결정론적 품질 지표가 나빠지지 않는 것입니다. 비용은 기록하되 당분간 기준으로 쓰지 않습니다(7장).

## 2. 현재 상태 진단

### 2.1 품질 문제의 구조적 원인

| 증상 | 원인 | 현재 대응 |
| --- | --- | --- |
| 보조 논문 서술이 얕음, 초록에 기댄 메타 문장 | 무엇을 읽을지 코드가 미리 고정(서베이 핵심 논문만 arXiv HTML, 보조 논문은 초록, DOI만 있으면 PDF도 안 읽음) | 없음 |
| 같은 수치가 여러 절에서 반복 | 근거가 단위로 관리되지 않아 "이미 쓴 사실"을 코드가 모름. 앞 절 요약을 프롬프트로 넘기고 평가자가 찾기를 기대 | 평가 프롬프트 조항 |
| 근거 없는 주장 | 작가가 근거 묶음 전체를 보고 자유롭게 쓴 뒤, 사실 확인이 사후에 문장을 고침 | 사실 확인 호출, 표적 수정 |
| 0–100점 평가 → 재작성 반복의 효과 한계 | 외부 신호 없는 자기 비판 반복은 개선이 작거나 역효과(Huang et al., ICLR 2024). 판정 편차도 큼 | 최고 점수 초안 유지, 순위 규칙 |
| 학회 표기 오류(Zenodo, "Lecture notes") | 서지 판단이 휴리스틱("arXiv가 아닌 첫 위치") | 없음 |
| 비교표 셀 품질 | 표 셀이 자유 서술 카드 필드에서 그대로 옴 | 카드 프롬프트 조항 |
| 수식·마크업 잔실수 | 프롬프트 규칙 + 사후 정규식 197개 | 규칙 추가 |

결함마다 프롬프트 조항, 정규식, 다시 묻는 호출을 덧붙여 왔습니다. `docs/design.md`의 예외 규칙과 정규식 197개가 그 흔적입니다. 근거를 무엇으로 삼을지와 근거를 어떻게 추적할지가 구조에 없어서 규칙을 더해도 같은 종류의 결함이 다시 나옵니다.

### 2.2 기존 결과물과 작업 이력 검토

2026-11-03에 블로그 생성 PR 47개, 블로그의 사람 수정 PR(#86, #88, #89, #98, #117, #119, #121), scholar-lens 커밋 138개, 2026-10-11부터의 작업 대화, 로컬 실행 로그와 산출물(`papers/`, `logs/`)을 검토했습니다. 주요 사실입니다.

- 목표("블로그에 들어간 뒤 사람이 고칠 일이 없는 글")는 아직 달성되지 않았습니다. 현재 생성기로 만든 글(ToolOrchestra 요약, Strands 가이드, 에이전트 보안 서베이)도 손으로 고친 뒤 병합했고, #109와 #110은 막는 문제를 안고 열려 있습니다.
- 사람이 고친 것은 문장보다 정밀도입니다. 사실·수치 오류가 약 40건(틀린 변형·행의 수치, "공개 모델 중 최고"를 "최고"로 넓힘, 7B를 7억으로, 상대 %와 %p 혼동, 원문에 없는 수식·코드·알고리즘), 틀린 arXiv 링크가 약 42개(16개 글), 마크업·수식 수정이 약 28개 파일, 번역투 수정이 약 15건입니다.
- 같은 결함군이 3–14번 "수정"됐습니다. 정규식·프롬프트로 고친 수식, 문체, 메타 문장, 반복, 인용 링크는 다시 나왔고, 구조를 바꾼 수정(arXiv 그림 출처 교체, 블로그 규칙 게이트, arXiv ID 결정론적 검증)만 재발 기록이 없습니다.
- 평가 → 수정 반복은 점수와 막는 문제 수를 줄였지만(가이드 막는 문제 51 → 14, 서베이 152 → 43), 호출의 약 40%를 쓰고 실패한 서베이 절의 절반은 끝까지 통과하지 못했습니다. 점수는 76–86 사이에 몰려 판별력이 낮습니다. 사실 확인은 점수를 매긴 뒤 절을 고치고(중앙값 14줄 변경, 최대 −35%) 다시 평가하지 않습니다.
- 절 사이 중복은 절 단위 평가로 잡히지 않습니다. RLHF 서베이 6개 중 5개에서 비교 절 수치의 대부분(42–53개 중 39–51개)이 앞 절에 이미 있었고, 보안 서베이 비교표는 59개 중 54개가 반복이었습니다.
- 읽기 깊이가 역할에 묶여 있습니다. RLHF 서베이는 핵심 논문 14편이 전부 전문, 보조 논문 8편이 전부 초록이었습니다. 그런데 개요는 초록만 읽은 논문에 절 제목을 주었고, 그림이 있는 논문은 28편 중 13편뿐입니다.
- 조립에서 내용이 사라진 사고가 있었습니다. 보안 서베이의 생성 원본에서 한 절과 소절 셋이 통째로 빠졌고(원인은 Batch 로그 확인 필요), 핵심 논문 하나가 본문에 한 번도 나오지 않았습니다.
- 결정론적 검사가 맨 끝에 있습니다. 발행 단계에서만 거부된 실행에 약 30달러를 썼습니다(통제 태그 없음, 태그에 섞인 XML, 코드 펜스 안 `#` 주석을 H1로 본 검증기 오탐).
- 카드 캐시 키에 프롬프트 해시가 들어 있어 프롬프트를 고칠 때마다 카드 22개를 처음부터 다시 만들었습니다(4일에 4번). 단계별 토큰 기록이 없어 비용이 어디서 나가는지 로그로 알 수 없습니다.
- 좋은 글의 공통점(Insights 글, ToolOrchestra 요약, Zep 리뷰의 좋은 대목): 주장을 담은 제목, 구체적 실험 하나로 시작해 그 한계를 바로 밝힘, 추상 전에 일상적 예, 설계를 대안과 비교해 이유를 설명, 숫자가 든 작은 계산 예, 한 번 쓴 사실은 다시 쓰지 않고 쌓아 감, 글쓴이의 판단을 논문의 주장과 구분. 약한 글은 원문 구조를 따릅니다. 리뷰는 TL;DR 뒤에 `## 초록`(28개 중 13개)을 두고 같은 수치를 서너 번 반복하며 논문 결론을 다시 풀어 끝납니다. 가이드는 문서 순서대로 흘러 아키텍처가 1,000줄 뒤에 나오고 출처 54개 중 53개가 공식 문서입니다. 서베이는 연표, 논문 절, 비교표가 같은 결과를 되풀이합니다.

### 2.3 코드 위생

- 모듈 51개가 `src/` 한 층에 있고, 6개 파일이 1,100줄을 넘습니다. `TechGuideGenerator`는 1,105줄, `PaperReviewer`는 650줄입니다.
- 절 수정 엔진이 둘입니다(`explainer._section`, `section_loop.revise_section`). 가이드와 서베이의 래퍼도 거의 같은 코드입니다.
- 같은 코드가 여러 곳에 있습니다. 체인 구성 5곳, 설명 재질문 4곳, 발행 요청 조립 3곳, 태그 안 JSON 파서 2곳이고, 모델 팩토리 인스턴스는 9개입니다.
- 구조화 출력 방식이 넷입니다(태그 파서, 태그 안 JSON, find/replace 블록, `ast.literal_eval`).
- 계층 누수가 있습니다. `Paper`가 `explainer`에 있고, `config`가 `src`를, `jobs`가 `survey_plan`을 import하며, 순수 lint가 규칙 파일을 읽습니다.
- 전역 상태와 숨은 I/O가 많습니다. 환경 변수를 읽는 모듈이 9개이고, 비밀값이 `os.environ`을 거쳐 전달됩니다. HTTP 스택이 둘(requests, httpx)이고, 생성자가 I/O를 하므로 테스트가 `__new__`로 생성자를 우회합니다. import 시점의 부수 효과도 있습니다.
- 예외 처리가 일관되지 않습니다. `except Exception`이 43곳이고, 예외 객체에 `run_notes`나 `job_result` 같은 속성을 임의로 붙이며, 도메인 오류가 관련 없는 모듈에 흩어져 있습니다.

### 2.4 유지하는 취지와 새 위치

재구성은 기존 기능을 버리는 일이 아닙니다. 지금 규칙이 지키려는 목적은 그대로 두고, 프롬프트 조항이나 사후 정규식으로 흩어진 것을 근거 장부, 스키마, 검증기 같은 구조로 옮깁니다.

| 지금의 장치 | 지키려는 취지 | 새 위치 |
| --- | --- | --- |
| 출처 권한(`SOURCE_AUTHORITY`): 플래그·기본값은 공식 문서, 개념·내부 구조는 참고 자료도 가능 | 식별자와 값은 권위 있는 출처로만 | 근거의 `authority` 필드. Verify가 식별자 주장에 공식 문서 근거를 요구 |
| 리뷰 계획의 난이도·중요도, 목표 분량, 개념 소유(`owned_elsewhere`) | 어려운 것은 깊게, 쉬운 것은 짧게, 한 개념은 한 절에서 | Outline 스키마(난이도, 중요도, 소유 개념과 근거) + 분량 정책(`ArtifactSpec`) |
| 원문 미배정 구간을 앞 절에 붙이는 보정 | 원문 내용이 조용히 빠지지 않게 | Outline 검증: 핵심 근거(방법, 결과, 한계)가 어느 절에도 배정되지 않으면 다시 묻기 |
| 용어집과 `[new]`/`[introduced]` 표시, 번역 지침 | 용어 일관성, 첫 사용에만 영어 병기 | 그대로 유지. 용어집을 `domain`의 값 객체로, 표시 계산은 Assemble 전 코드 검사로 |
| 한국어 문체 규칙(`KOREAN_STYLE`), `writing_issues` | 번역투 없는 "입니다"체 | 프롬프트 한 파일(데이터) + 닫힌 패턴 검사기. 뜻을 흐리는 문장만 막는 기준 유지 |
| 절 평가(0–100점)와 수정 반복 | 깊이, 흐름, 친절함의 기준을 생성 중에도 지킴 | 루브릭 검사로 전환: 점수 대신 위치와 인용이 붙은 문제만 내고, 그 문제만 Fix로 보냄. 점수는 오프라인 평가에서만 사용 |
| 사실 확인(grounding), 표적 수정, 수정본 순위 비교 | 근거 없는 주장 제거, 수정이 글을 망치지 않게 | 주장·근거 대조 Verify + 지목 문장 Fix. `lost_structure` 같은 회귀 방지 검사는 그대로 |
| 리뷰 전체 편집(find/replace, 유일 사본 보호) | 이어 붙인 절을 한 글로 다듬기 | Edit 단계로 유지. 구조화 출력(편집 목록 스키마)으로 바꾸고 같은 보호 규칙 적용 |
| 시각 요소 계획(리뷰 계획의 그림 배정, 가이드 개요의 visual hint, 서베이 개요의 그림·수식·추가 표, 코드가 만든 연표·비교표, 그림 캡션 alt, 출처 줄, 그림 로컬화) | 표, 수식, 그림, 코드가 풍부하고 제자리에 있게 | 그대로 유지하고 강화(3.4). 시각 자료도 근거로 기록하고 Outline이 배정하며 Verify가 배정대로 들어갔는지 확인 |
| 블로그 규칙 게이트(`post_conventions.yml`, 검증기, 드리프트 검사) | 블로그 CI를 통과하는 글만 PR로 | 그대로 유지. `domain/validation`과 `BlogRepository` 포트 |
| 두 단계 서베이(계획 파일 편집 → 쓰기), 카드 캐시 | 사용자가 논문·계보를 고르고, 비싼 읽기를 재사용 | 그대로 유지. 카드는 근거 장부 캐시로 일반화 |
| 서지 정보는 API, 의미 판단은 모델 | 사실은 결정론적으로 | 그대로 유지하고 학회 선택 규칙을 보강 |
| 인용 키 `[@id]`를 코드가 링크로 렌더링, arXiv ID 검증 | 인용이 틀리거나 지어낸 링크가 없게 | 그대로 유지. 근거 표시 `[[E#]]`에서 논문 인용으로 렌더링 |
| SSRF 방지 고정 전송, 속도 제한, `Retry-After` | 안전한 수집, 공급자 제한 준수 | 그대로 유지. 어댑터 공용 계층 |
| CLI·`JobRequest`·`JobResult`·종료 코드·Batch·SNS·매니페스트 | 실행 계약 | 그대로 유지. 계약 테스트도 그대로 |

## 3. 생성 방식: 자율 에이전트를 어디까지 쓸 것인가

### 3.1 선택지 비교

| 선택지 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| A. 현재 고정 파이프라인 유지 | 재현성, 비용 예측 | 읽을 범위가 고정되어 깊이에 한계. 규칙 누적 | 기각 |
| B. 전체를 자율 에이전트 하나로(Claude Agent SDK 등) | 구현이 짧아 보임, 탐색 유연 | 비용 4–15배, 실행마다 편차, 형식·서지·발행처럼 규칙으로 풀리는 단계까지 확률에 맡김. 게이트를 강제하기 어려움 | 기각 |
| C. 결정론적 뼈대 + 범위 제한 에이전트 노드 + 주장 단위 검증 | 깊이는 에이전트가, 사실·형식은 코드가 보장. 단계별 체크포인트와 비교 평가 가능 | 근거 장부라는 새 모델과 검증기가 필요 | 채택 |

근거입니다.
- Anthropic "Building effective agents"(2024-12): 잘 정의된 작업은 워크플로가, 단계 수를 예측할 수 없는 열린 문제는 에이전트가 맞고, 에이전트는 비용·지연을 성능과 맞바꾼다고 봅니다.
- Anthropic 멀티 에이전트 연구 시스템(2025-06): 성능 차이의 약 80%를 토큰 사용량이 설명했고, 인용은 조사가 끝난 뒤 별도 에이전트가 붙였습니다.
- STORM(NAACL 2024), OmniThink(EMNLP 2025), WebWeaver(2025): 개요 전에 다각도로 조사하고, 근거 메모리에 연결한 개요로 절별로 그 절의 근거만 꺼내 쓰는 방식이 중복·환각을 줄였습니다.
- Huang et al.(ICLR 2024): 외부 피드백 없는 자기 수정은 효과가 없거나 나빠집니다. FActScore(EMNLP 2023): 사실성은 주장 단위로 출처와 대조할 때 안정적으로 측정됩니다.

### 3.2 단계와 책임

```
Acquire ─► Read ─► Outline ─► Draft ─► Verify ─► Review ─► Fix ─► Edit ─► Assemble ─► Publish
코드       에이전트  구조화 1회  절별      코드+주장  루브릭    지목    전체    코드        코드
           (범위     (근거 배정) (배정     단위 대조  위치만    문장만  편집
            제한)                근거만)
```

| 단계 | 방식 | 산출물(체크포인트) |
| --- | --- | --- |
| Acquire | 코드. 소스 해석, 서지 정보(권위 있는 API), 전문 확보(arXiv HTML → PDF 파싱 → 초록 순서) | `SourceSet` |
| Read | 에이전트. 소스(논문·문서)마다 읽기 에이전트가 도구로 필요한 절을 읽고 근거를 기록 | `EvidenceLedger` |
| Outline | 구조화 출력 1회 + 코드 검증. 절마다 근거 ID와 시각 요소(그림, 표, 수식, 코드)를 배정하고 근거 하나는 한 절만 소유 | `Outline` |
| Draft | 절마다 1회. 배정된 근거와 이미 쓴 사실 목록만 받고 문장마다 `[[E12]]` 표시 | `SectionDraft[]` |
| Verify | 코드 검사(수치가 인용문에 있는지, 근거 중복 사용, 메타 문장, lint) + 주장·근거 대조 LLM 호출 | `VerificationReport` |
| Review | 루브릭 검사(깊이 적합성, 흐름, 친절함, 문체). 점수 없이 위치와 인용이 붙은 문제만 반환 | `ReviewIssues` |
| Fix | Verify·Review가 지목한 문장만 실패 사유와 함께 고치거나 지움(최대 1–2회). 남으면 문장 삭제 또는 PR 체크리스트 | 수정된 초안 |
| Edit | 리뷰·가이드·서베이의 전체 편집(절 사이 연결, 중복 소절). 편집 목록 스키마, 유일 사본 보호 | 편집된 본문 |
| Assemble | 코드. 근거 표시를 인용 링크로 바꾸고 표, 연표, 참고 문헌, front matter를 조립 | `Post` |
| Publish | 코드. 이미지 로컬화, 블로그 규칙 검증, S3, GitHub PR | `JobResult` |

0–100점 점수로 재작성 여부를 정하는 반복은 생성 경로에서 뺍니다. 평가 기준(깊이, 흐름, 친절함, 문체)은 Review 단계가 계속 보지만, 점수가 아니라 고칠 위치와 이유를 냅니다. 판정 모델의 점수는 오프라인 평가(7장)에서만 씁니다. 생성 중 수정은 Verify나 Review가 지목한 구체적인 실패 사유가 있을 때만 합니다.

### 3.3 읽기 에이전트

- 도구:
  - `outline_of(source)`: 절·그림·표 목록
  - `read(source, anchor)`: 절 단위로 읽기
  - `search_in(source, query)`: 소스 안 검색
  - `follow_citation(source, ref)`: 인용한 논문을 색인에서 찾아 초록 읽기
  - `web_search(query)`: 가이드만, 도메인 정책 적용
  - `record(claim, quote, locator, kind)`: 근거 기록. kind는 수치·방법·한계·관계 등
  - `record_visual(kind, locator, caption, why)`: 그림, 표, 수식, 코드 예시를 시각 근거로 기록. 그림은 원문 이미지 URL과 캡션, 표는 원문 셀, 수식은 원문 LaTeX, 코드는 원문 코드 블록
- `record`는 코드가 검증합니다. `quote`가 소스 원문에 실제로 있어야 하고(공백 정규화 후 부분 문자열), 수치는 `quote` 안에 있어야 합니다. 통과하지 못한 기록은 이유와 함께 거부되어 에이전트가 바로 고칩니다. 외부 신호가 있는 자기 수정입니다.
- 한도: 소스마다 `max_turns`, 토큰 상한, 전체 실행의 하드 예산. 한도에 이르면 그때까지의 근거로 진행하고 PR 체크리스트에 남깁니다.
- 서베이는 논문마다 읽기 에이전트를 병렬로 돌리고(동시 4개), 보조 논문도 전문을 읽되 목표 근거 수를 작게 둡니다. 근거 장부는 소스·모델·프롬프트 버전 키로 S3에 캐시합니다(지금의 카드 캐시를 일반화).
- 리뷰는 한 논문을 깊게 읽어야 하므로 절 단위 읽기 에이전트를 씁니다. 지금의 문장 번호 범위 배정은 근거 ID 배정으로 대체합니다.

### 3.4 시각 요소

시각 요소의 풍부함은 지금 설계의 취지이고 그대로 지킵니다. 지금은 프롬프트가 "필요한 곳에 표·수식·그림"을 요청하고 평가자가 부족하면 감점합니다. 새 구조는 시각 요소를 근거와 같은 방식으로 다룹니다.

- 수집: 읽기 에이전트가 `record_visual`로 그림(원문 이미지와 캡션), 원문 표, 핵심 수식(원문 LaTeX), 코드 예시를 기록합니다. 코드가 원문에 실제로 있는지 확인합니다. 서베이 보조 논문도 읽으므로 쓸 수 있는 그림과 수식이 늘어납니다.
- 배정: Outline이 절마다 시각 요소를 배정합니다. 깊이(deep, standard, brief)별 최소 시각 요소 수를 `ArtifactSpec`이 정하고(예: deep 절은 2개 이상), 비교는 표, 알고리즘은 코드나 수식, 구조는 그림처럼 내용 유형에 맞는 형태를 지시합니다. 같은 그림·표는 한 절에만 둡니다.
- 생성: 작가는 배정된 시각 요소를 본문에서 설명하며 놓습니다. 코드가 만드는 표(연표, 비교표, 결과표)는 근거의 수치로 셀을 채워 수치가 원문과 어긋나지 않습니다. 셀은 명사구이고 빈 값은 "정량 수치 없음"입니다.
- 검증: 배정된 시각 요소가 빠지면 Verify가 차단 문제로 보고 Fix로 보냅니다. 수식은 원문 LaTeX와 대조하고(매크로 정규화 후), 표는 셀 수와 머리글을, 그림은 로컬화와 캡션 alt를 확인합니다. Review는 시각 요소가 설명을 돕는지, 장식인지를 봅니다(루브릭 E).
- 그리지 않는 것: 원문에 없는 그림을 생성하지 않습니다. 개념도는 HTTP 렌더러(mermaid 등)를 쓰는 별도 기능으로 나중에 평가합니다.

### 3.5 프레임워크 선택

| 후보 | 판단 |
| --- | --- |
| Strands Agents | 채택. 프로세스 안에서 돌고 Bedrock Converse(Stream)가 기본 제공자. 도구 정의(`@tool`), 훅, 호출 한도, 사용량 지표, OpenTelemetry를 제공 |
| 자체 Converse 도구 호출 루프 | 대비책. Strands의 한계(아래)가 막히면 같은 포트 뒤에서 교체 |
| Claude Agent SDK | 기각. Claude Code 실행 파일을 하위 프로세스로 띄우고, Bedrock에서는 Invoke API만, 내장 WebSearch 없음, 비용은 SDK 추정치, root에서 `bypassPermissions` 불가 |
| LangGraph | 불필요. 뼈대는 종류별로 선형이고 단계 체크포인트는 산출물 저장소로 충분 |
| AgentCore Harness | 기각. 커스텀 게이트를 강제할 루프 제어가 가장 적음 |

Strands에서 쓰는 기능(문서 기준 2026-11-03, Python SDK v1.63.0, 2026-10-30)은 다음과 같습니다.

- 모델: `BedrockModel(model_id, boto_session, boto_client_config, max_tokens, cache_config, additional_request_fields)`. 추론 프로필 ID를 그대로 `model_id`로 씁니다. 응용 추론 프로필 ARN은 캐시 자동 감지가 안 되므로 `CacheConfig(strategy="anthropic")`를 명시합니다.
- 한도: 호출마다 `limits`(turns, total tokens, output tokens)를 주고, 결과의 중단 사유(`limit_turns`, `limit_total_tokens` 등)로 한도 도달을 구분합니다. Python은 에이전트 트리 전체에 한도와 사용량을 합산합니다.
- 게이트: `BeforeToolCallEvent`(`cancel_tool`, 입력 수정), `AfterToolCallEvent`(결과 교체, 재시도), `AfterToolsEvent`(`end_turn`)로 도구 호출을 검사하고 막습니다. `record` 도구의 인용문 검증과 읽기 범위 제한을 여기에 둡니다.
- 구조화 출력: Pydantic 모델을 도구 명세로 바꿔 검증하고, 시도 횟수 상한이 있습니다.
- 지표: 실행 결과의 사이클별 토큰 사용량과 지연, OpenTelemetry 추적을 `Metrics` 포트로 보냅니다. 비용은 모델 레지스트리의 가격표로 계산합니다(지금과 같음).

Strands의 확인된 제약과 대응입니다.

- 확장 추론(thinking)을 켠 채 구조화 출력을 강제하면 Bedrock이 거부합니다("Thinking may not be enabled when tool_choice forces tool use", 이슈 #1485, 2026-01). 구조화 출력이 필요한 단계(Outline, 판정, 편집 목록)는 thinking 없이 호출하거나, 에이전트가 스스로 부르는 `submit(...)` 도구로 결과를 받습니다. 구현 첫 단계에서 현재 버전으로 다시 확인합니다.
- adaptive thinking과 effort는 `additional_request_fields`로 넘겨야 하고, 모델별 허용 값이 다릅니다. 모델 레지스트리가 모델별 요청 필드를 정합니다(지금 `factories.py::_build_model_config`의 역할).
- 문서가 빠르게 바뀝니다(마이너 버전마다 기능 추가). `strands-agents`는 마이너 버전까지 고정하고, 갱신은 평가셋을 통과한 뒤에만 합니다.

langchain 의존성(`langchain-core`, `langchain-aws`, `langchain-community`, `faiss-cpu`)은 제거하고 모든 LLM 호출을 Strands `BedrockModel`로 일원화합니다. 코드 검색의 FAISS 임베딩은 저장소 파일을 읽는 도구(`search_in`)로 대체할 수 있는지 평가한 뒤 결정합니다.

## 4. 목표 구조

### 4.1 패키지

```
scholar_lens/
  domain/            순수 코드. 외부 라이브러리는 pydantic만
    sources.py       Source, Paper, DocPage, Bibliography, Venue
    evidence.py      Evidence, EvidenceLedger(검증 규칙 포함)
    outline.py       Outline, SectionPlan, 근거 소유 규칙
    post.py          SectionDraft, Post, FrontMatter
    survey.py        SurveyPlan, 병합·순위·간선
    markdown/        lint, math, 표, 인용 렌더링(규칙은 Conventions 값으로 받음)
    validation.py    블로그 규칙 검증(post_validator)
    specs.py         ArtifactSpec: review, summary, guide, survey
    errors.py        InputRejected, SourceUnavailable, BudgetExhausted, PublishRejected ...
  application/
    ports.py         Protocol 정의(4.2)
    engine/          acquire, read, outline, draft, verify, fix, assemble 단계 함수
    use_cases.py     run_review, run_summary, run_guide, plan_survey, write_survey, publish
    run.py           run_job: JobRequest → JobResult, 오류 분류, RunNotes
  adapters/
    bedrock/         Strands BedrockModel 구성, 에이전트 실행기, 모델 레지스트리·가격·요청 필드, 토큰 계수
    scholarly/       arxiv, datacite, openalex, semantic_scholar, crossref, dblp
    web/             httpx 크롤러(SSRF 고정 전송), tavily, brave
    documents/       arXiv HTML 파서, PDF 파서(PyMuPDF, Upstage), 그림 추출
    aws/             S3 산출물 저장소, SSM 비밀값, SNS 알림, CloudWatch 지표, Batch 제출
    github/          블로그 브랜치·PR 동기화, 규칙 파일 조회
    filesystem.py    로컬 산출물 저장소
  prompts/           프롬프트 텍스트와 버전(데이터). 문체 규칙은 한 파일
  entrypoints/
    cli.py, worker.py
  bootstrap.py       조립 루트: Settings → 어댑터 → 유스케이스
  settings.py        pydantic-settings. 환경 변수와 config.yaml은 여기서만 읽음
```

의존 방향은 `entrypoints → bootstrap → application → domain`과 `adapters → application.ports, domain`뿐입니다. `import-linter` 계약으로 CI에서 강제하고, 지금의 `tests/test_architecture.py`를 대체합니다.

### 4.2 포트

| 포트 | 메서드(요지) | 어댑터 |
| --- | --- | --- |
| `LanguageModel` | `structured(prompt, schema)`, `text(prompt)` | Strands `BedrockModel`, 테스트용 스크립트 모델 |
| `AgentRunner` | `run(task, tools, limits) -> AgentOutcome`(결과, 중단 사유, 사용량) | Strands `Agent`, 테스트용 스크립트 에이전트 |
| `PaperIndex` | `resolve(id)`, `search(query, years)`, `references(ids)` | DataCite·arXiv, OpenAlex, Semantic Scholar, DBLP(학회명) |
| `DocumentReader` | `fetch(url) -> Document`(절·그림·표 구조) | arXiv HTML, PDF, 웹 페이지 |
| `WebSearch` | `search(query, domains)` | Tavily, Brave, 없음 |
| `ArtifactStore` | `get/put(key)` 체크포인트·캐시·결과 | S3, 로컬 |
| `BlogRepository` | `conventions()`, `find_post()`, `open_pr()` | GitHub |
| `Notifier`, `Metrics` | 실행 결과 알림, 지표 | SNS, CloudWatch, 없음 |
| `Clock` | 현재 시각 | 시스템, 고정 시계 |

재시도는 어댑터만 소유합니다. 대상은 요청 제한, 시간 초과, 일시적 연결 오류, 재시도 가능한 5xx이고 `Retry-After`와 상한이 있는 지수형 간격을 씁니다. 응용 계층은 재시도 가능 여부로 분류된 도메인 오류만 받습니다. 구조화 출력의 형식 오류는 `LanguageModel` 어댑터가 오류를 붙여 1회만 다시 묻습니다.

### 4.3 횡단 관심사

- 설정과 비밀값: `Settings`가 한 번 읽고 검증합니다. 비밀값은 `Secrets` 값 객체로 어댑터 생성자에 넘기며 `os.environ`에 쓰지 않습니다.
- HTTP: httpx 하나로 통일하고, SSRF 방지 고정 전송을 어댑터 공용으로 둡니다. `arxiv` 라이브러리와 requests는 제거합니다.
- 실행 메모: `RunNotes`를 유스케이스의 명시적 반환값으로 다룹니다. 예외에 속성을 붙이지 않습니다.
- 비용과 예산: `LanguageModel` 어댑터가 호출마다 토큰·비용을 `Budget`에 기록하고, 단계는 `Budget`을 확인합니다. 예산 초과는 `BudgetExhausted` 도메인 오류입니다.
- 단계별 사용량: 모든 모델 호출에 단계 이름을 붙여 단계별 토큰·비용을 실행 결과(`JobResult`)와 지표에 남깁니다.
- 관측성: 단계마다 구조화 로그(실행 ID, 단계, 모델, 지연, 토큰, 비용, 재시도·대체 사유)를 남기고 체크포인트를 S3에 저장해, 실패한 실행을 단계부터 다시 돌리고 원인을 볼 수 있게 합니다.

## 7. 평가와 합격 기준

전환 전에 현재 main에서 기준선을 잽니다.

- 평가셋(`eval/sets/`): 리뷰 3, 요약 2, 가이드 3, 서베이 2. 사람이 고친 이력이 있는 입력을 우선합니다(DPO·Kimi K2·Zep 리뷰, ToolOrchestra 요약, Strands·Ray Serve·vLLM 가이드, 에이전트 보안·RLHF 서베이). 블로그 PR의 사람 수정 목록(#86, #88, #89, #117, #119, #121)이 정답 확인 항목이 됩니다. 입력, 모델·추론 프로필 ID, 프롬프트 버전을 고정합니다.
- 결정론적 지표:
  - 근거 없는 주장 비율: 주장·근거 대조 결과
  - 근거 중복 사용 수와 같은 수치의 재등장 수
  - 서지 정확도: 학회·연도의 정답표 대비
  - 블로그 lint·검증 위반 수, 메타 문장 수
  - 사람 수정 재현율: 과거에 사람이 고친 항목 중 새 출력에서 다시 틀린 수
  - 문체 빈도: 1,000자당 재진술 접속어(이러한, 즉, 결국)와 강조어, Insights 글 대비
  - 전문 읽기 비율: 논문 중 전문을 읽은 비율
  - 시각 요소: 1만 자당 그림·표·수식·코드 수, Outline이 배정한 시각 요소 중 본문에 들어간 비율, 깨진 이미지·수식 수
  - 비용, 소요 시간
- 판정 모델: `eval/ARTIFACT_RUBRIC.md`, 작가와 다른 모델, 순서를 섞어 3회 실행한 중앙값을 씁니다. 사람이 표본을 주기적으로 확인합니다.
- 합격 기준:
  - 결정론적 지표가 모두 기준선보다 나쁘지 않습니다.
  - 근거 없는 주장 비율과 반복 수는 절반 이하입니다.
  - 판정 중앙값이 기준선보다 낮지 않습니다.
  - 글당 비용과 소요 시간은 기록만 하고 합격 조건으로 쓰지 않습니다(2026-11-03 결정). 서베이 기준선은 약 18달러입니다.

## 8. 전환 계획

한 브랜치에서 한 번에 재구성하되, 커밋은 아래 순서로 나누고 각 단계에서 테스트를 통과시킵니다.

1. 평가 도구와 기준선: 현재 main으로 평가셋을 실행해 수치를 기록합니다(비용 발생, 승인 필요).
2. 뼈대: `settings`, `bootstrap`, `ports`, 도메인 오류, `import-linter` 계약을 만듭니다.
3. 도메인 이전: markdown·math·검증·계획 스키마·병합·순위 같은 순수 코드를 동작 변경 없이 옮기고 기존 테스트를 따라 옮깁니다.
4. 어댑터: Bedrock Converse와 도구 루프, 서지 색인, 문서 읽기, 웹, AWS, GitHub를 옮깁니다. 계약 테스트와 HTTP 녹화 테스트를 둡니다.
5. 엔진과 서베이: 결함이 가장 많은 서베이를 새 엔진으로 먼저 구현하고 평가셋으로 비교합니다.
6. 가이드, 리뷰, 요약: 같은 엔진으로 옮기고 각각 평가합니다.
7. 진입점: CLI·worker를 새 유스케이스에 연결하고, CLI·작업 계약 테스트와 Docker 계약 검사를 그대로 통과시킵니다.
8. 정리: 옛 모듈과 langchain 의존성을 지우고, `docs/design.md`를 새 구조 기준으로 다시 씁니다.
9. 검증: 평가셋 전체, 원격 E2E, `cdk deploy` 후 Batch 실행을 확인합니다.

테스트는 `tests/unit`(도메인·응용, 가짜 포트)과 `tests/integration`(어댑터, 녹화 응답, moto)으로 나눕니다. 생성자에 I/O가 없으므로 `__new__` 우회와 모듈 전역 monkeypatch를 없앱니다.

## 9. 위험과 결정할 사항

결정된 사항(2026-11-03):

- 에이전트 실행기는 Strands Agents입니다.
- 점수 기반 재작성 반복은 생성 경로에서 빼고, 평가 기준은 위치가 붙은 문제를 내는 Review 단계로 유지합니다.
- 비용 상한은 당분간 두지 않습니다. 하드 예산은 폭주 방지용으로만 둡니다.
- 기존 장치의 취지는 유지합니다(2.4).
- 시각 요소(그림, 표, 수식, 코드)의 풍부함은 잃지 않습니다. 근거로 기록하고 배정·검증합니다(3.4).

남은 사항:

- ❓ 평가셋과 서지 정답표: 입력 목록과 학회·연도 정답을 함께 확정해야 합니다.
- ❓ Strands의 thinking과 구조화 출력 충돌이 현재 버전에서도 남아 있는지 구현 첫 단계에서 확인합니다.
- 위험: 한 번에 재구성하면 리뷰 범위가 커집니다. 단계별 커밋, 계약 테스트, 평가셋 비교로 회귀를 잡습니다.
- 위험: 근거 인용문 검증이 PDF 추출 텍스트의 줄바꿈·하이픈에 약할 수 있습니다. 정규화 규칙을 문서 어댑터에 두고 실패율을 지표로 봅니다.
- 위험: 읽기 에이전트의 실행마다 편차가 생깁니다. 근거 장부를 캐시하고 체크포인트에서 다시 실행해 재현합니다.
