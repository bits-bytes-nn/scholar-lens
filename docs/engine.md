# 일반화한 근거 장부 엔진 설계

리뷰·요약·가이드·서베이를 하나의 엔진으로 쓰고, 글 종류별 차이는 선언적 명세(`PostSpec`)로만 표현하는 설계입니다. 현재 구조(`docs/design.md`)와 재설계 경과(`docs/redesign.md`)를 전제로 합니다.

## 1. 왜 다시 설계하는가

- 세 엔진(`guide_engine.py`, `paper_engine.py`, `survey_engine.py`)의 흐름은 같습니다: 근거 읽기 → 개요(최대 3회 수리) → 잘못된 근거 제거 → 절 순차 작성(초안 → 검사·수정 반복) → 전체 검토 → TL;DR → 마무리. 그런데 이 흐름이 엔진마다 복제되어 장치가 비대칭으로 붙었습니다. 반복 검토는 논문·가이드에만, 빈 절 제거는 가이드에만 있고, 서베이에는 전체 검토가 없습니다. 같은 `GlossaryTerm`이 세 번 정의되어 있습니다.
- 판정 결함을 사례마다 막아 왔습니다(특정 정책이 예제를 막는 경우, 특정 SDK 언어, 특정 표). 장치가 사례에 묶이면 다른 입력에서는 효과가 없고 프롬프트와 코드만 늘어납니다.
- 판정에서 반복된 결함의 원인은 일반적입니다.
  - 근거 없음으로 판정된 문장이 노트만 남기고 발행됩니다.
  - 수정 뒤에는 결정론적 검사가 다시 돌지 않습니다.
  - 편집 보호 장치가 중복 제거를 막습니다.
  - 핵심 내용이 빠졌는지 확인하는 장치가 없습니다.
  - API 검사가 호출 형태 일부만 봅니다.
  - 출처의 신뢰도와 버전을 한곳에서 정하지 않습니다.

## 2. 설계 원칙

1. 엔진은 글 종류를 모릅니다. 종류별 차이는 `PostSpec`의 데이터와 작은 훅으로만 들어옵니다. 엔진 코드에 `if post == "summary"` 같은 분기를 두지 않습니다.
2. 규칙은 근거와 출처의 속성으로 씁니다. 근거 종류, 출처 신뢰도, 버전, 언어·SDK, 날짜가 그 속성입니다. 제품·논문·호스트 이름과 평가 항목의 문장은 코드와 프롬프트에 넣지 않습니다. 프롬프트 예시는 평가셋과 무관한 가상의 예로 둡니다.
3. 의미 판단은 LLM이 구조화 출력으로 하고, 수락·거부·적용은 코드가 합니다. 의미 판단에는 이 문장이 근거로 뒷받침되는지, 같은 사실인지, 반복인지가 들어갑니다. 정규표현식은 안정된 형식(Markdown 블록, 인용 표시, 수치)에만 씁니다.
4. 모든 변경은 같은 검증을 통과합니다. 초안, 절 수정, 전체 검토 수정, 반복 제거가 모두 하나의 편집 트랜잭션(4.4)을 거칩니다. 어느 경로로 들어온 문장도 검사를 건너뛰지 못합니다.
5. 실패는 숨기지 않습니다. 검사가 돌지 못했으면 발행을 막거나 PR 차단 항목으로 올립니다. "노트만 남기고 통과"는 사람이 판단할 항목에만 씁니다.
6. 단계 산출물은 입력 해시로 저장합니다. 다시 실행하면 같은 입력의 단계를 재사용하고, 실패한 실행은 이어서 진행합니다.

## 3. 구성 요소

```
PostSpec (글 종류별 데이터)          SourceSet (출처와 신뢰도·버전)
        │                                   │
        ▼                                   ▼
┌──────────────────────── PostEngine ─────────────────────────┐
│ read → plan(outline + coverage) → write(sections) →          │
│ post passes(consistency, repetition, coverage) → tldr → final│
│                                                              │
│ 공통 장치: Verifier 묶음 · EditTransaction · VerdictCache ·  │
│            Checkpoint 저장소 · ModelCallPolicy               │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 PostSpec

글 종류 하나를 정의하는 불변 데이터입니다. 엔진은 이것만 보고 동작합니다.

| 필드 | 뜻 | 리뷰 | 요약 | 가이드 | 서베이 |
| --- | --- | --- | --- | --- | --- |
| `kinds` | 절 종류와 순서 순위, 개수(정확히 1, 1 이상, 선택) | tldr, problem, method+, implementation?, experiments+, analysis?, closing | 고정 다섯 절 + tldr | tldr, overview, concepts·architecture+, usage·operations+, choosing | introduction, lineage+, comparison, cross_cutting?, insights |
| `fixed_titles` | 코드가 정하는 제목 | tldr, closing | 다섯 절 모두 | tldr | 없음 |
| `evidence_policy` | 근거 종류별 허용 출처 신뢰도 | 설정·코드 금지 | 같음 | 설정·코드는 공식만 | 수치·한계는 표 칸 필수 |
| `routing` | 근거 종류의 기본 배정 절 | limitation → closing | 같음 | limitation → choosing | limitation → 비교 표 |
| `length` | 총 길이 범위와 깊이별 가중치 | 25k–55k | 2.5k–4.5k | 25k–45k | 논문 수 비례 |
| `runnable_kinds` | 독자가 실행하는 코드가 있는 절 | 없음 | 없음 | usage, operations | 없음 |
| `attachments` | 코드가 만들어 붙이는 블록 | 없음 | 없음 | 없음 | 연표(introduction), 비교 표(comparison) |
| `coverage` | 반드시 다룰 핵심 대상을 뽑는 출처와 개수 | 초록·서론의 핵심 주장 5–8개 | 3–5개 | 요청 문서 각 주요 절과 사용자 참고 자료 | 핵심 논문 각각과 계보 |
| `post_passes` | 전체 검토 종류 | 일관성, 반복, 포함 여부 | 같음 | 일관성(실행 예제 추적), 반복, 포함 여부 | 일관성, 반복, 포함 여부 |
| `prompts` | 읽기·개요·작성·검토 프롬프트의 종류별 본문 | `paper_evidence` | 같음 | `guide_evidence` | `survey_evidence` |

공통 규칙(문체, 수식, 표, 시각 요소, 주장 범위, 자기 지시 금지, 같은 사실, 반복)은 `prompts/rules.py`에 한 벌만 두고 모든 종류가 씁니다.

### 3.2 공통 데이터 모델

- `Section`: `kind`, `title`, `thesis`, `question`, `depth`, `evidence`, `topics`(가르칠 대상)와 종류별 확장 필드를 담습니다. 확장 필드는 서베이의 `papers`·`lineage` 같은 것으로, `extra: dict` 대신 종류별 하위 모델로 둡니다.
- `Outline[SectionT]`: `title`, `glossary`, `running_example`, `sections`, `same_facts`, `coverage`(핵심 대상 → 근거 id)를 담습니다. 서베이의 `short_names`·`table`은 확장 필드입니다.
- `GlossaryTerm`, 개요 검사(종류 순서와 개수, 근거 중복 배정, 미지의 근거, 빈 절), 길이 배분은 공통 함수 하나로 만들고 `PostSpec`을 인자로 받습니다.

### 3.3 SourceSet: 출처의 신뢰도와 버전을 한곳에서

출처마다 `authority`, `version`, `published`, `language`를 수집 단계에서 한 번 정합니다.

- `authority`는 official, official_repo, reference, third_party, forum 중 하나입니다.
- `version`은 문서 URL 버전, 저장소 태그, 패키지 릴리스 중 하나입니다.
- `language`는 SDK 언어입니다.

이후 단계는 이 값만 씁니다. 지금은 수집 단계와 작성 단계가 공식 여부를 따로 판정합니다.

- **목표 버전**: 실행마다 하나로 정합니다(기본값: 최신 정식 릴리스). 목표 버전과 다른 문서는 `older_docs` 또는 `dev_docs`로 표시하고, 그 사실을 근거로 쓸 때 버전을 밝히게 합니다.
- **순위와 상한**: 검색 결과는 신뢰도와 날짜로 순위를 매깁니다. 외부 글은 개수 상한을 두고, 포럼·소셜·집계 사이트는 설정 가능한 목록으로 낮춥니다.
- **수집 자료 저장본**: 수집 결과(검색어, 결과 URL, 본문)를 입력 해시로 저장합니다. 평가와 재실행은 같은 수집 자료를 쓸 수 있습니다.

## 4. 공통 장치

### 4.1 Verifier 묶음

검사는 이름이 있는 검증기로 등록합니다. 각 검증기는 `(post_state, section) -> list[Problem]`을 돌려줍니다. `Problem`은 종류, 위치, 문구, 차단 여부를 담습니다.

| 검증기 | 판단 주체 | 적용 범위 |
| --- | --- | --- |
| structure | 코드 | 모든 절: 제목, 코드 블록 짝, 유일한 그림·수식·표 |
| evidence_markers | 코드 | 미지의 근거, 다른 절 근거, 이미 한 번 되짚은 근거 |
| numbers | 코드 | 근거 인용문·수식·코드에 없는 수치(근거 `scope`는 지지 근거로 치지 않음), 표 행 인용에 열 머리 첨부 |
| claims | LLM | 문장을 원자 사실로 나눠 근거 대조(`unsupported_parts`) |
| api_surface | 코드 | 패키지 소스 색인(언어별 어댑터)으로 import 경로, 함수·클래스·데코레이터·속성 호출의 키워드 인자 확인 |
| program | 코드 | 실행 대상 절의 코드를 읽는 순서대로 이어 붙여 정의되지 않은 이름과 구문 오류 확인 |
| rules | 코드 | 블로그 작성 규칙(`quality_gate`) |
| coverage | 코드 | 핵심 대상마다 근거가 배정되고 본문에서 인용되었는지 확인 |
| repetition | LLM | 글 전체에서 같은 사실·예제·코드가 반복되는지 판단 |

- 검증기 묶음은 `PostSpec`이 고르고, 엔진은 모든 변경 지점에서 같은 묶음을 실행합니다.
- 패키지 색인이 일부만 만들어졌거나 지연 export가 있으면 "없음" 판정을 내지 않습니다. 지연 export는 모듈의 `__getattr__`, `__all__`, 조건부 import로 판단합니다.
- 언어별 색인은 어댑터로 둡니다. Python은 `ast`, 다른 언어는 색인이 있을 때만 적용합니다.

### 4.2 VerdictCache

`claims` 검증기의 판정은 아래 요소의 묶음을 키로 저장합니다.

- 문장
- 바로 앞 문장
- 인용한 근거 id
- 절 근거 목록의 지문
- 원문 발췌의 지문

수정 회차와 전체 검토에서는 바뀐 문장과 그 다음 문장만 다시 판정합니다. 앞 문장을 키에 넣는 이유는 지시어가 가리키는 대상이 바뀐 경우를 다시 보기 위해서입니다.

### 4.3 수정 요청

검사 결과는 하나의 수정 요청으로 모읍니다. 수정은 구절 교체·삭제(`SectionEdits`)로 받습니다. 편집이 하나도 적용되지 않을 때만 절 전체를 다시 받습니다. 지금 방식과 같습니다.

깊이·친절함처럼 내용을 늘리는 지적에는 반드시 근거 id를 달게 합니다. 근거 없이 설명을 덧붙였다가 다음 회차에 근거 없음으로 지워지는 순환을 막기 위해서입니다.

### 4.4 EditTransaction

절 수정, 전체 검토 수정, 반복 제거, 근거 없는 부분 삭제가 모두 이 트랜잭션을 거칩니다.

1. **적용**: 편집 묶음을 순서대로 적용합니다. 위치가 한 번만 나오지 않는 편집은 건너뜁니다.
2. **최종 결과 검증**: 중간 상태가 아니라 묶음의 최종 결과를 검증합니다.
   - 코드 블록 짝, `##` 제목 목록이 유지돼야 합니다.
   - 그림·수식·표·코드 블록은 같은 내용의 사본이 글 어딘가에 남아 있을 때만 지울 수 있습니다.
   - 작성 규칙 위반이 새로 생기면 안 됩니다.
3. **실패 처리**: 최종 결과가 실패하면 편집을 하나씩 적용하는 방식으로 되돌아가 통과하는 편집만 남깁니다.
4. **검증기 재실행**: 그 절의 검증기 묶음을 다시 돌립니다. 문제 집합을 비교할 때는 위치 숫자를 지워 정규화합니다. 새 문제가 생긴 편집 묶음은 받지 않습니다.
5. **새 문장 확인**: 트랜잭션이 새로 만든 문장은 `claims`로 확인합니다. 근거와 모순되면 지웁니다. 근거 없음이면 4.5의 처리를 따릅니다.

### 4.5 근거 없는 문장의 처리

1. 근거 없는 부분(`unsupported_parts`)만 좁히는 최소 수정을 한 번 요청합니다(RARR).
2. 다시 판정해 여전히 근거 없음이면 그 문장을 지우고, 앞뒤 문장이 이어지게 다듬습니다.
3. 표 행, 코드, 작성자 예시 표시(`[[EX]]`)가 붙은 문장, 마무리 절의 평가 문장은 지우지 않고 PR 확인 항목으로 올립니다.
4. 한 절에서 지울 문장이 전체의 25%를 넘으면 검사 쪽 오작동으로 보고 지우지 않습니다. 대신 PR을 차단 항목으로 표시합니다.

### 4.6 포함 여부(coverage)

1. **추출**: 계획 단계에서 `PostSpec.coverage`가 정한 출처로 핵심 대상을 뽑습니다. 구조화 호출 한 번입니다.
2. **읽기**: 읽기 에이전트는 이 목록을 받아 해당 근거를 먼저 기록합니다.
3. **개요**: 개요는 대상마다 근거 id를 배정합니다(`coverage`). 코드는 배정되지 않은 대상이 있으면 개요를 다시 요청합니다.
4. **TL;DR과 검증**: TL;DR은 핵심 대상의 근거를 인용해야 합니다. 마지막에는 본문 인용으로 다시 확인합니다.

### 4.7 글 전체 단계

- 모든 종류가 같은 순서로 실행합니다: 일관성 검토 → 반복 검토 → 포함 여부 확인 → TL;DR → 마무리.
- 가이드의 실행 예제 추적은 일관성 검토의 옵션입니다(`PostSpec.post_passes`).
- 각 검토의 지적은 해당 절의 수정 요청이 되어 4.4를 거칩니다.

### 4.8 앞 절 맥락

다음 절 작성자에게는 두 가지를 줍니다.

- 코드가 만든 "이미 가르친 것" 목록: 각 절의 제목, 인용한 근거의 주장, 정의한 코드 이름
- 직전 한두 절의 본문

글 전체 본문을 60k자까지 넣는 지금 방식보다 입력이 작고, 긴 글에서도 앞부분이 잘리지 않습니다.

### 4.9 Checkpoint 저장소

다음 단계 산출물을 입력 해시로 저장합니다.

- 수집 자료
- 근거 장부
- 핵심 대상
- 개요
- 확정된 절
- 전체 검토 결과

다시 실행하면 해시가 같은 단계는 다시 쓰고, 실패한 실행은 마지막으로 저장한 단계부터 이어서 진행합니다. 발행 단계에서 거절된 글도 같은 저장소에서 다시 발행할 수 있습니다(`publish` 명령).

### 4.10 ModelCallPolicy

- 캐시 지점은 호출이 명시합니다. 공유 접두부가 있는 호출만 그 끝에 캐시 지점을 둡니다. 한 번만 쓰는 프롬프트는 캐시에 쓰지 않습니다. 지금은 Strands가 마지막 사용자 메시지 끝에 캐시 지점을 자동으로 붙입니다.
- 절의 사실 확인 맥락은 "앞 절 근거(커지기만 함) → 이 절 근거" 순서로 둡니다. 앞부분이 다음 절의 캐시와 맞게 하기 위해서입니다.
- 검사가 구조화 답을 끝내 내지 못하면 차단 문제로 남깁니다. 지금처럼 통과로 치지 않습니다.

## 5. 과적합을 막는 장치

- **평가셋 분리**: 개발용 항목(Strands, vLLM, Zep, LoRA, RLHF 서베이)과 확인용 항목(Ray Serve, DPO, Kimi, ToolOrchestra, 보안 서베이와 새 항목)을 나눕니다. 기본값 변경은 확인용 항목에서 판단합니다.
- **사례 문장 금지**: 프롬프트와 코드에 평가 글의 문장, 제품·논문 이름, 사례별 분기를 넣지 않습니다. 테스트의 정규 데이터는 가상의 예로 둡니다.
- **회귀 테스트의 형태**: 버그 수정의 회귀 테스트는 사례가 아니라 성질을 고정합니다. 예를 들어 "속성 호출의 미지 키워드는 문제로 보고된다"처럼 씁니다.
- **평가 절차**: 판정마다 새 세션을 쓰고 판정자를 가립니다. 수집 자료를 고정하고, 설정마다 생성을 2회 합니다. F는 40개 이상 주장의 오류율로 봅니다. 차이가 잡음의 2배 이상일 때만 채택합니다.

## 6. 전환 단계

각 단계는 테스트가 모두 통과한 상태로 끝냅니다. 평가 비용이 드는 단계는 따로 승인을 받습니다.

| 단계 | 내용 | 끝나는 조건 |
| --- | --- | --- |
| E1 | `PostSpec`, 공통 `Section`·`Outline`·개요 검사·길이 배분, `PostEngine`의 read → plan → write → post passes → tldr 흐름. 세 엔진은 명세와 훅만 남김 | 기존 엔진 테스트가 같은 결과로 통과 |
| E2 | Verifier 묶음, EditTransaction, VerdictCache, 근거 없는 문장 처리, 검사 실패 차단 | 성질 테스트(트랜잭션, 정규화 비교, 캐시 재사용, 25% 상한) |
| E3 | 글 전체 단계 통일(서베이 포함), 포함 여부(coverage), 앞 절 맥락 목록 | 종류별 시나리오 테스트 |
| E4 | `api_surface` 일반화(속성 호출, 데코레이터, 지연 export, 일부만 만든 색인), `numbers`의 `scope` 제외와 표 머리 | 성질 테스트 |
| E5 | ModelCallPolicy, Checkpoint 저장소와 `publish`·재개, PR 실패 종료 코드, 쓰지 않는 코드 색인과 `public_assets` 삭제 | CLI 계약 테스트 |
| E6 | SourceSet(신뢰도·버전·날짜 한곳에서, 검색 순위·상한, 수집 자료 저장본) | 수집 단위 테스트 |
| E7 | 5의 절차로 평가: 확인용 항목 포함, 엔진당 생성 2회, 독립 판정 | 리뷰·요약에서 근거 장부 엔진이 기준선 이상이면 `sections` 엔진 삭제 |
