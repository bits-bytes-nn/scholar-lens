# 일반화한 근거 장부 엔진과 아키텍처 재설계

리뷰·요약·가이드·서베이를 하나의 엔진으로 쓰고, 글 종류별 차이는 선언적 명세(`PostSpec`)로만 표현하는 설계입니다. 출력물 품질, 코드·아키텍처 위생, 운영(AWS Well-Architected), 테스트·CI·문서를 함께 다룹니다. 현재 구조는 `docs/design.md`, 재설계 경과와 평가 결과는 `docs/redesign.md`에 있습니다.

## 1. 진단

### 1.1 출력물

판정(`eval/runs/`)에서 반복된 결함은 사례가 달라도 원인이 같습니다.

| 결함 | 원인 단계 | 지금의 대응 | 한계 |
| --- | --- | --- | --- |
| 근거보다 넓은 서술, 출처에 없는 귀속 | 작성, 수정 | 근거 없음 판정 뒤 노트만 남김 | 문장이 그대로 발행됨 |
| 같은 사실·예제·코드의 반복 | 작성(앞 절 본문이 잘림), 수정 | 같은 사실 묶음, 반복 검토(가이드·논문만) | 편집 보호 장치가 삭제를 막음, 서베이는 검토 없음 |
| 핵심 결과 누락, TL;DR이 부차적 결과를 앞세움 | 읽기, 개요 | 읽기 지시의 우선순위 | 포함 여부를 확인하는 장치가 없음 |
| 없는 API 인자, 붙여 넣으면 깨지는 코드 | 작성, 수정 | import한 이름 호출의 키워드 검사, 구문·이름 검사 | 속성 호출·데코레이터·지연 export를 못 봄, 수정 뒤에는 검사 안 함 |
| 오래되거나 다른 버전의 사실 | 수집 | URL 버전으로 오래된 문서 표시 | 한 실행 안에 latest·stable·main과 다른 패키지 버전이 섞임 |
| 형식(제목, TL;DR, 마무리, 표 칸) | 개요, 작성 | 종류별 개요 검사 | 엔진마다 다른 코드 |

### 1.2 코드·아키텍처

- **흐름 복제**: 세 엔진(`application/*_engine.py`, 약 2,100줄)이 같은 흐름을 따로 구현합니다. 근거 읽기 → 개요(수리 반복) → 잘못된 근거 제거 → 절 작성·검사·수정 → 전체 검토 → TL;DR → 마무리입니다. 장치가 엔진마다 다르게 붙고, `GlossaryTerm`과 개요 검사도 세 벌입니다.
- **사례에 묶인 장치**: 근거 규칙 함수(`_no_code`, `_no_code_or_settings`, `authority_rule`), 정규식으로 코드 정의를 뽑는 `defined_in_code`, 엔진별 상수(`_RUNNABLE_KINDS`)가 일반 규칙이 아니라 엔진에 박혀 있습니다.
- **레거시 계층 `scholar_lens/src`**: 유스케이스(`*_pipeline.py`), 웹 수집(1,466줄), 파싱, 발행, 이전 엔진(`explainer.py`, `summarizer.py`, `section_loop.py`), 프롬프트가 섞여 있습니다. 계층 계약은 `domain`·`application`·`adapters`에만 걸려 있습니다.
- **엔진 두 벌**: 리뷰·요약은 이전 엔진(`sections`)이 기본이고, 설정 상당수가 두 엔진 중 한쪽에서만 동작합니다.
- **숨는 실패**:
  - 사실 확인이 답을 내지 못해도 통과로 칩니다.
  - PR 생성에 실패해도 `succeeded`로 끝납니다.
  - 근거 장부 엔진은 읽기 단계만 저장해, 실패한 실행을 재개할 수 없습니다.

### 1.3 평가

- 가이드 v11, 논문 v4, 서베이 v12 이후의 "3회 판정"은 한 세션에서 나온 판정이라 독립적이지 않습니다.
- 개발용과 확인용 항목이 나뉘어 있지 않습니다.
- F의 판정 편차가 평균 1.2점이라, 그보다 작은 차이로는 결정할 수 없습니다.

## 2. 원칙

1. **엔진은 글 종류를 모릅니다.** 종류별 차이는 `PostSpec`의 데이터와 이름이 붙은 작은 훅으로만 들어옵니다. 엔진 코드에 글 종류 분기를 두지 않습니다.
2. **규칙은 속성으로 씁니다.** 근거 종류, 출처 신뢰도, 버전, 언어, 날짜가 그 속성입니다. 제품·논문·호스트 이름, 평가 글의 문장, 사례별 분기는 코드와 프롬프트에 넣지 않습니다. 프롬프트 예시는 평가셋과 무관한 가상의 예로 둡니다.
3. **판단과 실행을 나눕니다.** 의미 판단(지지 여부, 같은 사실, 반복, 핵심 대상)은 LLM이 구조화 출력으로 하고, 수락·거부·적용·계산은 코드가 합니다. 정규표현식은 Markdown 블록, 인용 표시, 수치처럼 형식이 안정된 대상에만 씁니다.
4. **모든 변경은 같은 검증을 통과합니다.** 초안, 수정, 전체 검토, 반복 제거가 모두 하나의 편집 트랜잭션을 거칩니다.
5. **실패는 드러냅니다.** 검사가 돌지 못하면 PR 차단 항목이 되고, 발행 실패는 실패로 보고합니다. "노트만 남기고 통과"는 사람이 판단할 항목에만 씁니다.
6. **숫자는 설정으로 둡니다.** 상한·비율·개수는 근거를 적은 명세나 설정 값이며, 함수 안에 박지 않습니다.
7. **단일 출처를 둡니다.** 출처의 신뢰도·버전, 글 종류 규칙, 공통 작성 규칙, 모델 역할·가격은 각각 한곳에서 정합니다.

## 3. 출력물 품질 계약

각 품질 차원을 어떤 장치가 보장하고 누가 판정하는지 정합니다. 모든 장치는 글 종류에 관계없이 같고, 기준값만 `PostSpec`에서 옵니다.

| 차원 | 보장 장치 | 판정 |
| --- | --- | --- |
| 구성 | 절 종류·순서·개수 규칙(`PostSpec.kinds`), 고정 제목, 개요 검사 하나 | 코드 |
| 전개 | 절마다 논지와 독자 질문, 앞 절에서 가르친 것 목록(4.8), 되짚기 문장의 대상 확인, 실행 예제의 일관성(4.7) | 코드, LLM |
| 형식 | 블로그 규칙의 결정적 후처리와 검증(`quality_gate`, `validation`), 수식·표·코드 블록 규칙 | 코드 |
| 내용 | 원문 인용 근거, 원자 사실 단위 확인(4.1 claims), 포함 여부(4.6), 출처 신뢰도·버전(3.1), 근거 없는 문장 처리(4.5) | 코드, LLM |
| 표현 | 공통 작성 규칙(`domain/prompts/rules.py`), 용어집의 첫 등장 표기와 일관성, 반복 검토 | 코드, LLM |
| 시각 요소 | 그림을 근거로 기록하고 배정, 수치 근거로 표를 만드는 코드(종류 공통: 결과 비교 표, 서베이 연표), 코드 블록, 유일한 그림·수식·표 보호 | 코드 |

### 3.1 출처 정보의 단일 출처(SourceSet)

출처마다 아래 네 가지를 수집 단계에서 한 번 정합니다. 이후 단계는 이 값만 씁니다.

- `authority`: official, official_repo, reference, third_party, forum 중 하나
- `version`: 문서 URL 버전, 저장소 태그, 패키지 릴리스 중 하나
- `published`: 발행 날짜
- `language`: SDK 언어

이 값을 바탕으로 다음을 처리합니다.

- **공식 범위**: 요청한 문서 페이지가 공식으로 만드는 호스트의 경로 범위입니다. 저장소 호스트는 저장소(테넌트)까지, 경로에 문서 버전(`v0.6.0`, `0.6`, `r2.10`, `latest` 등)이 있으면 그 버전까지(다른 버전도 같은 문서)로 정합니다. 버전이 없으면 처음 가져온 요청 페이지의 같은 호스트 링크(탐색·본문)를 보고, 그 링크 중 `tech_guide.official_scope_link_share`(기본 0.6) 이상이 들어가는 페이지 경로의 가장 깊은 접두부를 범위로 둡니다. 여러 제품, 블로그, Q&A가 한 호스트에 있어도 요청한 제품 문서만 공식이 됩니다. 링크가 없으면 페이지 경로의 첫 구간까지, 사이트 루트를 요청했을 때만 호스트 전체입니다. 숫자만 있는 경로 구간(`/3/`)은 API 버전이나 쪽 번호와 구분할 수 없어 버전으로 보지 않습니다.
- **목표 버전**: 실행마다 하나로 정합니다(기본값: 최신 정식 릴리스). 목표 버전과 다른 문서의 사실은 버전을 밝혀 씁니다.
- **검색 결과**: 신뢰도와 날짜로 순위를 매기고, 외부 글은 개수 상한을 둡니다. 가져오는 결과 중 일부(`tech_guide.min_secondary_pages`, 기본 3)는 공식이 아닌 1차 자료(논문, 설계 문서와 글, 참고 수준의 페이지)에 남겨 공식 문서가 모든 자리를 채우지 못하게 합니다. 이 몫도 외부 글 상한 안에서만 채우고, 낮출 출처 종류는 몫에 세지 않습니다. 낮출 출처 종류(포럼, 소셜, 집계 사이트)는 설정 목록으로 둡니다.
- **수집 자료 저장본**: 수집 결과를 입력 해시로 저장해 재실행과 평가에서 다시 씁니다.

## 4. 엔진

```
PostSpec ──┐            SourceSet ──┐
           ▼                        ▼
 PostEngine: read → plan(outline + coverage) → write(sections)
             → post passes(consistency, repetition, coverage) → tldr → final
 공통 장치: Verifier 묶음 · EditTransaction · VerdictCache · Checkpoint 저장소
            · ModelCallPolicy
```

### 4.0 PostSpec

| 필드 | 뜻 |
| --- | --- |
| `kinds` | 절 종류, 순서 순위, 개수(정확히 1, 1 이상, 선택), 기본 깊이 |
| `fixed_titles` | 코드가 정하는 제목(언어별) |
| `evidence_policy` | 근거 종류별로 허용하는 출처 신뢰도, 필수 필드(예: 수치의 표 칸), 언어 일치 조건 |
| `routing` | 근거 종류의 기본 배정 절(예: 한계 → 마무리) |
| `length` | 총 길이 범위와 깊이별 가중치 |
| `runnable_kinds` | 독자가 실행하는 코드가 있는 절 |
| `attachments` | 코드가 만들어 붙이는 블록(표, 연표)과 그 절 |
| `coverage` | 핵심 대상을 뽑는 출처와 개수 범위 |
| `post_passes` | 글 전체 검토의 종류와 옵션(실행 예제 추적 등) |
| `prompts` | 읽기·개요·작성·검토 프롬프트의 종류별 본문 |
| `limits` | 수정 회차, 개요 수리 횟수, 삭제 상한 비율, 앞 절 맥락 크기, 수정이 보는 앞 절 근거 수, 짧은 초안 재요청 비율, 너무 긴 절의 기준 배수(`max_length_share`), 깊이별 시각 요소 최소 개수(`min_visuals`), 읽기 에이전트의 후속 턴·재요청 횟수·절 길이, 출처별 근거 개수 범위 |

리뷰·요약·가이드·서베이의 명세는 `domain/specs/`에 데이터로 둡니다. 공통 작성 규칙은 `domain/prompts/rules.py` 한 벌입니다.

### 4.1 Verifier 묶음

검증기는 `(PostState, section) -> list[Problem]`입니다. `Problem`은 종류, 위치, 문구, 차단 여부를 담습니다. 묶음은 `PostSpec`이 고르고, 엔진은 모든 변경 지점에서 같은 묶음을 실행합니다.

| 검증기 | 판정 | 내용 |
| --- | --- | --- |
| structure | 코드 | 제목, 코드 블록 짝, 유일한 그림·수식·표 |
| evidence_markers | 코드 | 미지의 근거, 다른 절 근거, 이미 되짚은 근거 |
| numbers | 코드 | 인용문·수식·코드에 없는 수치. 근거의 `scope`는 지지 근거로 치지 않고, 표 행 인용에는 열 머리를 붙임 |
| claims | LLM | 원자 사실 단위의 근거 대조 |
| api_surface | 코드 | 패키지 소스 색인(언어별 어댑터)으로 import 경로, 함수·클래스·데코레이터·속성 호출의 키워드 확인. 일부만 만든 색인이나 지연 export면 "없음" 판정을 내지 않음 |
| program | 코드 | 실행 대상 절 코드를 읽는 순서대로 이어 붙여 정의되지 않은 이름과 구문 오류 확인(`ast`, 정규식 아님) |
| rules | 코드 | 블로그 작성 규칙 |
| coverage | 코드 | 핵심 대상의 근거 배정과 본문 인용 |
| repetition | LLM | 글 전체의 같은 사실·예제·코드 반복 |

### 4.2 VerdictCache

`claims` 판정은 아래 다섯 요소의 묶음을 키로 저장합니다.

- 문장
- 바로 앞 문장
- 인용한 근거 id
- 절 근거 목록의 지문
- 원문 발췌의 지문

수정 회차와 전체 검토에서는 바뀐 문장과 그 다음 문장만 다시 판정합니다.

### 4.3 수정 요청

검사 결과는 한 번의 수정 요청으로 모읍니다. 수정은 구절 교체·삭제로 받고, 편집이 하나도 적용되지 않을 때만 절 전체를 다시 받습니다. 내용을 늘리라는 지적에는 근거 id를 반드시 달게 합니다.

### 4.4 EditTransaction

1. 편집 묶음을 적용하고, 최종 결과를 검증합니다.
   - 코드 블록 짝과 `##` 제목 목록이 유지돼야 합니다.
   - 그림·수식·표는 글 어딘가에 사본이 남을 때만 지울 수 있습니다. 코드 블록은 독자가 읽는 순서대로 실행하므로, 같은 절이나 앞 절에 사본이 남을 때만 지울 수 있습니다. 뒤 절에만 사본이 있으면 첫 사본을 지울 수 없습니다.
   - 작성 규칙 위반이 새로 생기면 안 됩니다.
2. 최종 결과가 실패하면 편집을 하나씩 적용하는 방식으로 돌아가, 통과하는 편집만 남깁니다.
3. 그 절의 검증기 묶음을 다시 돌립니다. 위치와 숫자를 지워 정규화한 문제를 다중집합으로 비교해, 옮겨지거나 고쳐 쓴 같은 문제는 그대로 두고 한 형태의 문제가 늘어난 편집 묶음은 받지 않습니다. 다만 지운 그림·수식·표마다 다른 절에 사본이 있으면(반복 제거), 그 삭제로 생긴 시각 요소 최소 개수(`Limits.min_visuals`) 미달은 새 문제로 보지 않습니다. 사본은 그 절이 소유하므로 이 절의 개수에 세지 않고, 최소 개수는 절이 자기 시각 요소를 갖추라는 작성 목표이지 중복을 붙잡아 두는 규칙이 아니기 때문입니다. 글 전체 수정 뒤에도 남은 문제는 PR 노트에 남깁니다.
4. 새로 생긴 문장은 claims로 확인합니다. 근거와 모순되면 지우고, 근거 없음이면 4.5를 따릅니다.

### 4.5 근거 없는 문장

1. 근거 없는 부분만 좁히는 최소 수정을 한 번 요청합니다(RARR).
2. 여전히 근거 없음이면 그 문장을 지우고 앞뒤를 잇습니다.
3. 표 행, 코드, 작성자 예시 표시, 마무리 절의 평가 문장은 지우지 않고 PR 확인 항목으로 올립니다.
4. 지울 문장이 한 절의 `limits.max_drop_share`를 넘으면 검사 쪽 오작동으로 보고 지우지 않습니다. 대신 PR을 차단 항목으로 표시합니다.

### 4.6 포함 여부(coverage)

1. 계획 단계에서 `PostSpec.coverage`의 출처로 핵심 대상을 뽑습니다(구조화 호출 한 번).
2. 읽기 에이전트는 이 목록을 받아 해당 근거를 먼저 기록합니다.
3. 개요는 대상마다 근거를 배정합니다. 배정 안 된 대상이 있으면 코드가 개요를 다시 요청합니다. 그 대상을 말할 출처(서베이 계보는 그 계보의 논문)에 근거가 하나도 없으면 어떤 개요도 배정할 수 없으므로 다시 요청하지 않고 PR 메모로 남깁니다. 다시 요청한 개요가 구조 규칙을 어기면 앞서 받은 구조상 문제없는 개요 중 배정 안 된 대상이 가장 적은 것을 메모와 함께 씁니다.
4. TL;DR은 핵심 대상의 근거를 인용해야 합니다.
5. 마지막에 본문 인용으로 다시 확인합니다.

### 4.7 글 전체 단계

모든 종류가 같은 순서로 실행합니다.

1. 일관성 검토: 실행 예제 추적, 되짚기 대상, 용어 일관성
2. 반복 검토
3. 포함 여부 확인
4. TL;DR
5. 마무리

각 지적은 해당 절의 수정 요청이 되어 EditTransaction(4.4)을 거칩니다. 실행 가능한 절이 있는 종류(`PostSpec.runnable_kinds`)는 그 트랜잭션 안에서 글 전체 프로그램 검사(`python_code_problems`, 읽는 순서)도 돌립니다. 다른 절의 코드에 프로그램 문제를 하나라도 더하는 수정은 받지 않습니다.

### 4.8 앞 절 맥락

다음 절 작성자에게는 두 가지를 줍니다.

- 코드가 만든 "이미 가르친 것" 목록: 각 절의 제목, 인용한 근거의 주장, `ast`로 찾은 코드 정의
- 직전 `limits.previous_sections`개 절의 본문

### 4.9 Checkpoint 저장소와 재개

다음 단계 산출물을 입력 해시로 저장합니다.

- 수집 자료
- 근거 장부
- 핵심 대상
- 개요
- 확정된 절
- 전체 검토 결과

각 단계의 입력 해시에는 그 단계를 만드는 역할의 모델 ID, 추론 강도와 대체 모델이 들어갑니다. 근거 캐시 키에는 읽기 역할의 모델이 들어갑니다. 역할 하나의 모델을 바꾸면 그 역할이 만드는 단계와 이후 단계만 다시 실행합니다.

실패한 실행은 마지막으로 저장한 단계부터 이어서 진행합니다. 발행 단계에서 거절된 글은 `publish` 명령으로 다시 검증해 PR을 엽니다.

### 4.10 ModelCallPolicy

- 캐시 지점은 호출이 명시합니다. 공유 접두부가 있는 호출만 캐시에 씁니다.
- 사실 확인 맥락은 "앞 절 근거 → 이 절 근거" 순서로 둡니다.
- 구조화 답이 끝내 없으면 차단 문제로 남깁니다.

## 5. 아키텍처

### 5.1 계층

| 계층 | 위치 | 담는 것 | 의존 가능 대상 |
| --- | --- | --- | --- |
| domain | `scholar_lens/domain` | 근거·개요·명세, 검증기 중 코드 판정, 편집 트랜잭션, Markdown, 블로그 규칙 | 표준 라이브러리, pydantic |
| application | `scholar_lens/application` | `PostEngine`, 유스케이스(생성, 발행, 재개, 상태, 비용), 포트 | domain |
| adapters | `scholar_lens/adapters` | Bedrock·Strands, 웹 수집·검색, 학술 색인·문서, 패키지 색인, S3, GitHub, Batch | domain, application의 포트 |
| entrypoints | `scholar_lens/cli.py`, worker, `bootstrap` | 인자 해석, 설정 로드, 의존성 조립 | 모두 |

- **포트**: `LanguageModel`, `SourceGateway`(수집·검색), `DocumentReader`(논문·PDF), `PackageIndex`, `CheckpointStore`, `PostPublisher`, `RunLedger`, `Files`(로컬 경로와 `s3://` 위치의 파일. 유스케이스는 파일을 이 포트로만 읽고 씁니다)
- **`scholar_lens/src` 해체**:
  - 유스케이스는 application으로 옮깁니다.
  - 입출력은 adapters로 옮깁니다.
  - 이전 엔진은 `legacy/` 하나로 모아 삭제 기준(8장 E9)을 기다립니다.
  - 해체가 끝나면 `src`를 지웁니다.
- **계층 계약**: import-linter로 고정합니다. 엔트리포인트 외에는 설정 모듈(`configs`)을 읽지 않고, 설정은 생성자 인자로 받습니다.

| 지속 가능성 | 중복 호출 제거, 재개로 재실행 낭비 방지 |

## 6. 테스트·CI·문서

- **테스트 구성**: `tests/unit`(domain, application, 가짜 포트)와 `tests/integration`(어댑터, 녹화 응답, moto)으로 나눕니다.
  - 버그 수정의 회귀 테스트는 사례가 아니라 성질을 고정합니다. 예: "속성 호출의 모르는 키워드는 문제로 보고된다".
  - 계약 테스트: CLI·작업 JSON, 포트 구현, 명세 4종의 개요 규칙
  - 엔진 시나리오 테스트: 명세마다 가짜 모델로 읽기부터 마무리까지
- **CI**:
  - ruff, black, mypy(domain·application은 strict), import-linter, pytest
  - 커버리지 하한: 현재 수준
  - 의존성 취약점 검사(pip-audit)
- **문서**:
  - `docs/design.md`: 현재 구조로 다시 씀
  - 이 문서: 엔진과 아키텍처 정본
  - `docs/adr/`: 결정 이력(엔진 통합, 평가 절차, 이전 엔진 삭제)
  - README: 사용법과 운영 절차

## 7. 과적합 방지와 평가

- **평가셋 분리**: 개발용(Strands, vLLM, Zep, LoRA, RLHF 서베이)과 확인용(Ray Serve, DPO, Kimi, ToolOrchestra, 보안 서베이)으로 나눕니다. 기본값 변경은 확인용으로 판단합니다.
- **판정 절차**: 판정마다 새 세션을 쓰고 X·Y로 가립니다. 수집 자료를 고정하고, 설정마다 생성을 2회 합니다. F는 주장 오류율로 봅니다. 차이가 잡음의 2배 이상일 때만 채택합니다.
- **결정 지표**: 결정적 지표(반복률, 규칙 위반, 근거 없는 문장 수, 단계별 토큰·비용)와 A·C·T1을 우선합니다.
